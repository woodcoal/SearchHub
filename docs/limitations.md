# 已知限制与适用边界

**部署前请先读这一篇。** 这里列的是真实存在的限制，不是"未来会改进"的营销话术。如果你需要的能力正好在下面，SearchHub 可能不是合适的工具。

---

## 一、什么情况下不该用 SearchHub

如果符合以下任意一条，**直接调用上游搜索 API 更合适**，不需要引入这一层：

- 只有**一台机器**、**一个供应商**、**一把 key**
- 不需要给不同调用方分配独立额度
- 不需要审计"谁查了什么"
- 不需要密钥轮换与故障切换

SearchHub 的价值来自**多个消费者共享一组上游密钥**这个场景。只有一个消费者时，它只是多了一跳网络开销。

---

## 二、运行时状态在内存里，重启清零

以下状态保存在**进程内存**中，重启后归零：

- 密钥的**冷却 / 隔离**状态
- **当日、当月、累计**用量计数
- **熔断器**状态
- **用量统计**数据

影响：

- 重启后，之前被隔离的密钥会**立即重新可用**。如果某把 key 是真的失效了，重启后第一次调用会再次失败并被重新隔离（有一次无效请求的开销）。
- 重启后当日用量计数归零，可能导致**当天累计调用量超过配置的日配额**。对按次计费的套餐要留意。
- **多实例部署会出问题**：每个实例各自维护一套计费与熔断状态，配额无法全局生效。

**多实例部署需要把 `KeyPool` 与 `Stats` 换成 Redis 实现。** 接口已按可替换设计，但目前**尚未实现**。

> 持久化到磁盘的只有：供应商配置、密钥密文、调用方 API Key 哈希，以及 `calls.jsonl` 调用日志。

---

## 三、认证与会话

- 会话令牌和 API Key 都**没有服务端会话表**。
- 吊销 API Key **立即生效**。
- 但**已签发的后台登录令牌在过期前仍然有效**。要强制失效，**修改后台密码**（会话密钥混入密码哈希，改密码即失效全部旧令牌）。
- 没有任何内置的多用户 / 角色体系——管理后台是**单管理员密码**模型。多人协作需要共享这一个密码。

---

## 四、跨供应商降级时分页不连续

各家的分页语义不通用。当请求从供应商 A 降级到供应商 B 时，**翻页会从第一页重新开始**，无法接着之前的位置继续。

如果业务依赖深度翻页，建议：固定单一供应商，或只使用第一页结果。

---

## 五、能力覆盖差异

- **`safeSearch` 不被所有供应商支持**，传了会被记入 `meta.ignoredParams` 后忽略。
- **不支持图片检索和新闻检索**——目前只做 web 结果。
- 部分供应商**不支持翻页**（Tavily / Exa / AnySearch），传 `page` 参数无效。
- 想用这些能力需要直接调用对应供应商的原生 API。

---

## 六、存储规模

- 数据文件是**单个 JSON 文件 + 原子写入**，没有外部数据库依赖——这是为了部署简单。
- 适合**数百把密钥**这个量级。
- **密钥规模很大时**（数千把以上），单文件读写会成为瓶颈，建议换成真正的数据库。

---

## 七、日志的有界性

调用日志 `calls.jsonl` 只保留最近 **1000 条**，且读取时只取文件尾部 2MB。

- 这只是**运行观测**用途，不是审计留档。
- 需要长期审计请把日志导出到外部系统。
- 运行日志按天切分，默认保留 14 天。
